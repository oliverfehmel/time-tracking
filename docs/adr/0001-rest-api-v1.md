# ADR 0001: REST API v1 with personal API tokens

- Status: Accepted
- Date: 2026-11-05
- Deciders: Oliver Fehmel

## Context

Everything in the app is currently only reachable through the Twig UI. Users want to automate their time tracking
(start/stop the timer from scripts, sync entries from other tools, export reports) and admins want to integrate
user, absence and holiday data with other systems.

Requirements:

- Users, time entries, absences and holidays are fully available through an HTTP API.
- Every user can create their own API tokens. A token grants exactly what its owner may see in the UI: regular users
  their own data, admins all data.
- The API is documented with OpenAPI and browsable in Swagger UI.
- A page inside the app explains how the API works and links to Swagger UI.
- Half days (holidays, absence requests, quotas, `Settings::halfDaysEnabled`) behave exactly as in the UI.
- Everything is covered by automated tests.

Starting point: the business rules (date and overlap validation, quotas, approval workflow, notification mails,
time-entry locks, overlap resolution, timer) partly live in controllers, so an API would have duplicated them.

## Decision

### 1. Hand-written controllers + NelmioApiDocBundle, not API Platform

The API consists of thin Symfony controllers under `src/Controller/Api/` with request DTOs
(`#[MapRequestPayload]`, `#[MapQueryString]`) and response view classes (`src/Api/View/`). The OpenAPI document is
generated by **NelmioApiDocBundle 5** from routes, DTOs and `OpenApi\Attributes`.

API Platform was rejected: nearly every write has domain rules (quota, half-day, overlap, approval, mails), so every
operation would need a custom state processor, and its JSON-LD/Hydra defaults do not fit a small self-hosted app.
Nelmio ships Swagger UI as local assets — no CDN, which suits self-hosting.

### 2. Shared domain services

Before the API is added, the rules move out of the controllers into services that both the UI and the API call:

| Service | Responsibility |
|---|---|
| `AbsenceRequestService` | create (dates, half-day rules incl. feature toggle, overlaps via `AbsenceRequestValidator`/`DayPortion`, quota, auto-approval, admin mail), cancel, approve, reject (+ decision mail) |
| `TimeEntryService` | timer start/stop, create/update/delete with edit locks and overlap resolution (`TimeEntryOverlapResolver`) |
| `WorkLocationService` | set/clear the work location of a day (with edit locks) |

Rule violations are thrown as `DomainRuleViolation` (machine-readable `code`, translation key, parameters, HTTP
status). The UI turns them into form errors/flash messages, the API into problem responses. The UI behaviour stays
the same; new services get `ClockInterface` so tests can control "now".

### 3. Authentication: personal API tokens

- Entity `ApiToken`: `user` (cascade delete), `name`, `tokenHash` (SHA-256, unique), `tokenPrefix` (display only),
  `scope` (`read` | `read_write`), `createdAt`, `lastUsedAt`, `expiresAt` (nullable = never).
- Token format: `tt_` + 64 hex characters (32 random bytes). Only the hash is stored; the plain token is shown exactly
  once after creation.
- Managed by every user under **Profile → API tokens** (`/profile/api-tokens`): create (name, scope, expiry: 30/90/365
  days or never), list, revoke. Admins can list and revoke the tokens of any user on the user edit page, but cannot
  create tokens for others. Creating a token **while impersonating** is forbidden, otherwise an admin could keep
  persistent access as another user.
- Firewall `api` (`^/api/v1`), stateless, Symfony `access_token` authenticator with `ApiTokenHandler`,
  header `Authorization: Bearer tt_…`. No session, CSRF, remember-me or user switching. A session cookie does not
  authenticate API requests, and a token does not authenticate UI requests.
- `lastUsedAt` is written at most once per minute per token.
- Expired tokens are rejected (401). Revoked tokens are deleted.
- A `read` token gets 403 (`read_only_token`) on every non-GET request.
- Roles are reloaded on every request: demoting an admin immediately removes admin rights from their tokens.

### 4. Authorization

Voters decide per object (`TimeEntryVoter`, `AbsenceRequestVoter`, `UserDataVoter`, `HolidayVoter`):

| Data | Regular user | Admin |
|---|---|---|
| Users | read self | read, create, update, delete all |
| Time entries, timer, work locations, time report | own (with edit locks) | all users (edit locks do not apply) |
| Absence requests | own: read, create, cancel | all: read, create for anyone, cancel; approve/reject (not their own) |
| Absence quotas | read own overview | read all, set/remove |
| Absence types, work location types | read active | read all; create/update absence types |
| Holidays | read those assigned to them (without the user list) | read all incl. `userIds`, create/update/delete |

- Objects of other users answer **404** (no ID probing); admin-only endpoints answer **403**.
- A `userId` filter pointing to another user answers 403 for regular users.
- Edit locks for regular users are the same as in the UI: `Settings::usersAreAllowedToChangeTimeEntries` and
  `TimeTrackingCalculator::isEditableMonth()` (current and previous month). Admins writing through the API bypass both
  locks — in the UI they still apply to everybody, so the UI behaviour is unchanged.
- The team absence calendar (`/absences/overview`) is intentionally **not** exposed: through the API regular users
  only see their own data.

### 5. Conventions

- Base path `/api/v1`, JSON only (`Content-Type: application/json`).
- Every response body is an envelope:
  - single resource: `{"data": {…}}`
  - collection: `{"data": […], "meta": {"page": 1, "perPage": 50, "total": 123}}`
  - writes may add `meta`, e.g. `{"adjusted": true}` (time range was moved to a free slot) or
    `{"notificationSent": false}` (mail could not be sent).
- Pagination: `?page=1&perPage=50`, `perPage` max 200.
- Dates: `YYYY-MM-DD`. Points in time: ISO 8601 / RFC 3339 with offset, returned in the server time zone; input with
  any offset is converted.
- Durations: integer seconds. Day counts and quotas: decimal numbers (`0.5` steps).
- Language of error messages: from `Accept-Language` (`de` or `en`), otherwise the app default locale.
- Errors: RFC 9457 `application/problem+json`:

  ```json
  {
    "type": "about:blank",
    "title": "Unprocessable Content",
    "status": 422,
    "code": "validation_failed",
    "detail": "…",
    "violations": [{"propertyPath": "endDate", "message": "…", "code": "end_before_start"}]
  }
  ```

  | Status | Meaning |
  |---|---|
  | 400 | malformed JSON / query |
  | 401 | missing, unknown or expired token (`WWW-Authenticate: Bearer`) |
  | 403 | admin-only, read-only token, edit lock, own request approval |
  | 404 | unknown or foreign resource |
  | 409 | state conflict (timer already running, request not pending, duplicate email/key, user still referenced) |
  | 415 | wrong content type |
  | 422 | validation or domain rule violation |

### 6. Endpoints (v1)

| Method & path | Purpose |
|---|---|
| `GET /me` | own user, token scope/expiry, feature flags (`halfDaysEnabled`, `timeEntryEditingAllowed`) |
| `GET /users`, `GET /users/{id}` | users (regular users: only themselves) |
| `POST /users`, `PATCH /users/{id}`, `DELETE /users/{id}` | admin: manage users (`password` write-only; an admin cannot delete or demote themselves) |
| `GET /time-entries?userId&from&to` | time entries overlapping `[from, to)` |
| `GET /time-entries/{id}` | one entry |
| `POST /time-entries` | create a finished entry (`startedAt`, `stoppedAt`, admin: `userId`) |
| `PATCH /time-entries/{id}`, `DELETE /time-entries/{id}` | change/delete an entry |
| `GET /timer`, `POST /timer/start`, `POST /timer/stop` | own running timer |
| `GET /users/{id}/time-report/{year}` | per month and day: worked (Ist), target (Soll), balance, holiday/absence fractions, work location; Soll capped to today |
| `GET /work-location-types` | location types |
| `GET /users/{id}/work-locations?from&to` | explicit work locations |
| `PUT /users/{id}/work-locations/{date}`, `DELETE …` | set/clear the work location of a day |
| `GET /absence-types`, `POST /absence-types`, `PATCH /absence-types/{id}` | absence types (deactivate instead of delete) |
| `GET /absence-requests?userId&year&status` | absence requests |
| `GET /absence-requests/{id}` | one request incl. chargeable `days` |
| `POST /absence-requests` | create (admin: `userId`) |
| `POST /absence-requests/{id}/cancel` | cancel a pending or approved request |
| `POST /absence-requests/{id}/approve`, `…/reject` | admin decision (`reason` required for reject), sends mail |
| `GET /users/{id}/absence-quotas?year` | quota overview per active type (quota, used approved, used pending, remaining) |
| `PUT /users/{id}/absence-quotas/{year}/{typeId}`, `DELETE …` | admin: set/remove an individual quota |
| `GET /holidays?from&to&userId`, `GET /holidays/{id}` | holidays |
| `POST /holidays`, `PATCH /holidays/{id}`, `DELETE /holidays/{id}` | admin: manage holidays |

Running entries can only be created via `POST /timer/start`, so the "one running timer per user" invariant has a single
entry point.

### 7. Half days

- Absence requests expose `halfDay`, `dayFraction` (`0.5`/`1.0`) and `days` (chargeable days via
  `AbsenceDayCalculator::countForRequest()`, e.g. a full-day absence on a half-day holiday counts `0.5`).
- Writes with `halfDay: true` are only accepted while `Settings::halfDaysEnabled` is on (otherwise 422
  `half_days_disabled`). A half-day request must be a single day. Two half-day requests may share a day unless a
  half-day holiday already takes half of it (`DayPortion::fitsAlongside()`); every other overlap is rejected. The
  quota check uses the request's fraction.
- Holidays expose `halfDay`. With the feature off, `halfDay: true` is rejected for new holidays and for switching an
  existing one to half day; an existing half-day holiday keeps its flag when it is updated, and `PATCH` without
  `halfDay` leaves it unchanged (same as the form).
- Quotas (`quotaDays`, `defaultYearlyQuotaDays`) are numbers (`defaultYearlyQuotaDays: null` = unlimited, an
  individual `quotaDays: null` = use the type default), max 366, `0.5` steps while the feature
  is on, whole days otherwise; a stored half value stays valid (same rule as the forms).
- Existing half-day records are always reported and calculated as half days, regardless of the toggle — the toggle
  only controls input. Clients read the toggle from `GET /me`.

### 8. Documentation

- Swagger UI at `/api/docs`, OpenAPI JSON at `/api/docs.json`, both behind the normal login (main firewall). Bearer
  security scheme, so "Try it out" works with a pasted token.
- Guide page at `/api` (sidebar link "API"): token handling, scopes, auth header, curl examples, permissions, formats,
  pagination, errors, half-day rules, links to Swagger UI and the JSON document. German and English.

### 9. Tests

- `dama/doctrine-test-bundle` wraps every test in a transaction; functional tests run against the real test database
  (CI creates it and runs the migrations).
- Characterisation tests for the affected UI flows are written before the refactoring.
- API tests per resource: authentication, scoping (own vs. foreign vs. admin), validation, domain rules, half-day
  matrix (toggle on/off), mails.
- Contract tests: every `/api/v1` route is documented, and every JSON response in the functional tests is validated
  against the generated OpenAPI schema.

## Consequences

- One place for each business rule, used by UI and API. The UI controllers become thinner.
- New dependencies: `nelmio/api-doc-bundle` (and `zircote/swagger-php`), `symfony/clock` (direct), dev:
  `dama/doctrine-test-bundle`.
- New table `api_token` (migration).
- The test suite now needs a database (as CI already provided); local setup is documented in the README.
- The API is versioned in the path. Breaking changes require `/api/v2`; additive changes (new fields, endpoints) do not.

## Not in scope (possible follow-ups)

- OAuth2 / third-party apps, CORS for browser clients on other origins.
- Rate limiting per token.
- Webhooks.
- Settings, branding and work-location-type administration via API.
- Team absence calendar.
